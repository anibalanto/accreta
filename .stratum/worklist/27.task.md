# `CaptureGenerator`, y el plugin `spring-controller`

Señalás **sólo el método**, y el plugin sabe ir a buscar lo demás:

```
$ bilinker new --as spring-controller docs/spec.md:12:1 Controller.java:16:5
```

- sube a la clase y toma el `@RequestMapping`
- baja al método y toma el `@GetMapping`
- toma la firma sin el cuerpo

Cuatro fragmentos de una sola posición. **Y la ruta compuesta entra**, que es lo que [`1d`](1d.task.md) diagnosticó y no tenía salida: *"sale de un `@RequestMapping` de clase más un `@GetMapping` de método, y el literal completo no aparece en ningún lado"*.

## El plugin vive en la entrada y no deja rastro

Genera una query y desaparece. El capture resultante es **una query normal**: no dice quién lo generó, no depende de que el plugin exista, y se podría haber escrito señalando cuatro posiciones a mano.

**Y eso lo fuerza el formato, no la disciplina.** El id de un capture es `sha256(file \0 query \0)`; agregarle *"generado por spring-controller"* le cambiaría el id sin cambiar la ubicación. No hay dónde dejar el rastro aunque uno quisiera.

## La forma

```rust
pub trait CaptureGenerator {
    fn name(&self) -> &str;
    fn applies(&self, file: &str, node: Node) -> bool;
    fn query(&self, source: &str, node: Node) -> Result<String>;
}
```

Un `Vec<Box<dyn CaptureGenerator>>` que el binario arma. **Sin carga dinámica**: plugins `.so` es complejidad que todavía no pidió nadie, y el trait deja la puerta abierta.

## El modo se pide; no se adivina

`applies()` no sirve para **elegir** el modo, sólo para **sugerirlo**:

```
$ bilinker new docs/spec.md:12:1 Controller.java:16:5
capturado el método entero, con su cuerpo.
  sugerencia: `--as spring-controller` compone la ruta y deja el cuerpo afuera.
```

Un plugin que acierta cuando no querías **ya te escribió otra cosa**, y un capture es opaco después. Es la misma línea que el proyecto sostiene en otros lados: *bilinker arregla solo lo que es suyo, y pide lo que es del repo del usuario.*

## Y el ancla conviene que sea la ruta, no el nombre del método

El generador elige qué predicado escribe. Para un controller, anclar por el literal de la anotación:

```scheme
(#eq? @path "\"/permissions/from-token\"")
```

es más fiel que anclar por `getPermissions`: **un refactor renombra el método y no la ruta**, y lo que el bilink describe es el contrato. Es el reverso de lo que `1d` observó —*"una ruta no es un buen ancla si no existe como literal"*— porque el pedazo del método **sí** existe como literal.

## Cuándo está hecha

- Existe el trait, con al menos dos implementaciones: `interface` y `spring-controller`.
- `--as spring-controller` sobre un método de un controller Spring produce un capture de cuatro fragmentos.
- El capture generado es indistinguible de uno escrito a mano.
- La detección **sugiere y no elige**.
- El capture ancla por la ruta, y sobrevive a que el método se renombre — con un test.

## Lo que no entra

**Plugins cargables en runtime**, y **plugins para otros frameworks**. Spring es el caso real; el trait es lo que hace que el segundo sea agregar un archivo.

# `apply` culpa a git cuando el que cambió fue el anchor

Cuando un archivo se renombra **y** el símbolo capturado adentro también, `apply` falla con un mensaje que nombra la causa equivocada:

```
$ bilinker apply --dry-run
warn  36f0c759.1: MOVED: no se encontró la nueva ruta de
      'crates/bilinker/src/task.rs' en git diff -M
```

Pero git **sí** la había encontrado:

```
$ git diff -M --name-status HEAD
R087    crates/bilinker/src/task.rs    crates/bilinker/src/issue.rs
```

## Qué pasa de verdad

`apply.rs::compute_moved` recorre los renames de git, encuentra el destino, y antes de aceptarlo verifica que la query siga resolviendo ahí. Si no resuelve hace `continue` — y al terminar el loop cae en un `bail!` que atribuye el fracaso a que git no encontró el rename.

O sea: **el mensaje describe la primera condición del loop cuando la que falló fue la última.** El caso real es MOVED y REANCHORED juntos, que ningún estado expresa porque los dos son de resolución y el capture guarda uno solo.

## Por qué molesta

Manda a mirar el lugar equivocado. Quien lea eso va a revisar el índice de renames de git, que está bien, en vez del anchor, que es lo que cambió. Es la misma familia que la task `v`: la salida no es fiel a lo que la herramienta sabe.

Reproducido en la task `z`, al renombrar `task.rs` a `issue.rs` junto con `resolve_task_path` a `resolve_issue_path`.

## Qué haría falta

Distinguir los dos motivos de descarte y decirlo: *"el archivo se movió a X, pero el anchor `<nombre>` ya no está ahí — repuntar con `bilinker recapture`"*. La salida correcta no es un fix automático sino el nombre del comando que sí puede resolverlo.

Que no haya auto-fix está bien: la nueva ubicación del fragmento dentro del archivo destino es una inferencia que `apply` no debería hacer sola. Lo que está mal es no decir por qué.

## Cuándo está hecha

Renombrar un archivo y el símbolo capturado adentro produce un mensaje que nombra el anchor y sugiere `recapture`, con un test que lo fija.

## Una tercera causa, del mismo mensaje

Apareció otra vez al extraer el crate de formato, y con un motivo distinto: **el archivo destino no estaba trackeado.** `git diff -M` sólo ve lo que git conoce, así que un archivo nuevo sin `git add` es invisible y el rename no se detecta — el mensaje vuelve a decir que git no encontró la ruta, sin decir que falta stagearlo.

Son tres causas con un solo mensaje:

| Lo que pasó | Lo que hay que hacer |
|---|---|
| git no detectó el rename (el destino no está trackeado) | `git add` y volver a correr |
| el destino está, pero el anchor se renombró | `bilinker recapture` |
| el fragmento no está en ninguna parte | `recapture` o `remove` |

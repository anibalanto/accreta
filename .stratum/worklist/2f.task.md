# Publicar `lspd` y sacar los `path` que atan tres repos por el disco

[`29`](29.task.md) dejó esto anotado y no lo podía hacer: publicar un repo bajo una cuenta ajena no es una acción de quien programa. Ya existe `git@github.com:anibalanto/lspd.git`.

## Qué está mal mientras tanto

Tres `Cargo.toml` —`lattice`, `lattice-cli` y `bilinker-cli`— declaran el cliente así:

```toml
lspd-client = { path = "../../../../../lspd/.stratum/impl/crates/lspd-client" }
```

Cinco niveles de `../` que **atan dos repos independientes por cómo están acomodados en el disco**. Es exactamente lo que el modelo de capas evita, y lo que un clon suelto de lattice no puede satisfacer.

La forma correcta ya existe en el proyecto, y es cómo bilinker consume stratum:

```toml
stratum = { git = "https://github.com/anibalanto/stratum.git", branch = "main" }
```

## Cuándo está hecha

- El repo de lspd está publicado, con su historia.
- Los tres `Cargo.toml` declaran `lspd-client` por git, y ningún `path` cruza de un repo a otro.
- Lattice y bilinker compilan desde el git remoto, no desde el árbol de al lado.
- Los comentarios que explicaban el interinato se van con él.

## Lo que no entra

**Publicar los crates en crates.io.** Ninguno de los del ecosistema lo está, y una dependencia git es lo que el proyecto ya usa.

## Cómo cerró

`git@github.com:anibalanto/lspd.git`, con los dos commits de [`29`](29.task.md) y [`2a`](2a.task.md). Los tres `path` que cruzaban de un repo a otro se fueron; el único que queda es el de adentro de lspd —`lspd` → `lspd-client`—, que es del mismo workspace y es donde un path corresponde.

**Y ahora se compila contra el remoto de verdad.** No es un detalle de forma: el lockfile de lattice pasó a registrar

```
source = "git+https://github.com/anibalanto/lspd.git?branch=main#e91cf93c…"
```

o sea un commit, no una ruta del disco de alguien. Un clon suelto de lattice ya se puede buildear.

Verificado con un clon fresco: `git clone` del repo publicado, `cargo test`, los seis tests del transporte pasan.

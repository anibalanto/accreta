# El capture cubre el contrato y no el cuerpo

Como `retinar`, quiero que un bilink sobre un endpoint de `hsi` cubra **lo que ese endpoint promete** —su ruta y la forma que devuelve— y no cómo está implementado.

## Por qué, y es la mitad del MVP

Hoy un capture toma el **nodo con nombre entero**. Sobre un método de un controller eso incluye el cuerpo, y trae dos problemas opuestos:

| | |
|---|---|
| **de más** | un refactor interno mueve el hash y dispara drift que no es drift. [`1d`](1d.task.md) ya lo anotaba: *"su cuerpo cambia por refactors que no cambian el contrato"* |
| **de menos** | la ruta no entra, porque sale de **dos** anotaciones —`@RequestMapping` de clase y `@GetMapping` de método— y el literal completo no existe en ningún lado |

Y lo que rompió a `retinar` está justo ahí: espera `HSIRoleInfoDto[]` de una ruta que devuelve `FetchUserPersonFromTokenDto`. **El tipo de retorno está en la firma**, así que capturar la firma lo detecta — sin LSP, sin lattice, sin nada más.

## El mecanismo es uno solo

> **La query captura varios `@target`, y el fragmento es la concatenación.**

Hoy `find_target` devuelve el primero y descarta el resto. Con varios, el mismo mecanismo resuelve las dos cosas: *la firma sin el cuerpo* es capturar `type`, `name` y `parameters` y no `body`; *la ruta compuesta* es capturar dos anotaciones que están en nodos distintos.

**Y sigue siendo estructural.** No son rangos de bytes: si el método se mueve, la query lo encuentra igual, que es lo que bilinker existe para hacer.

## Las posiciones son la entrada, no lo que se guarda

Señalás con el cursor y bilinker genera la query. Es lo que [`capture.md`](../../subsystems/bilinker/concepts/capture.md) ya dice —*"la selección sirve para **encontrar** el nodo y después **se descarta**"*— aplicado a más de una.

Y encima de eso, dos atajos:

| | Quién sabe qué |
|---|---|
| N posiciones a mano | **nadie** sabe nada. Siempre funciona. |
| `--as interface` | bilinker sabe qué campo del nodo es el cuerpo, por gramática |
| `--as spring-controller` | **un plugin** sabe de Spring. Bilinker no. |

**Nunca se adivina el modo**: se sugiere. Un plugin que acierta cuando no querías ya te escribió otra cosa.

## Las tasks

| | |
|---|---|
| [`24`](24.task.md) | la query captura N `@target` |
| [`25`](25.task.md) | `new` con N posiciones, y la salida que deja ver qué se capturó |

| [`27`](27.task.md) | `CaptureGenerator`, y el plugin `spring-controller` |

`24` es el mecanismo y va primero; las otras tres son formas de generar esa query.

## Cuándo está hecha

- Un bilink sobre el método de un controller **no cambia de hash cuando cambia el cuerpo**.
- El mismo bilink **sí cambia** cuando cambia el tipo de retorno o un parámetro.
- La ruta compuesta —dos anotaciones en nodos distintos— entra en un solo capture.
- El modo se pide explícito; la detección sugiere y no actúa.
- Un plugin no deja rastro en el capture: el id sigue siendo `sha256(file \0 query \0)`.

## Lo que no entra

**El nivel 1** —los campos de `PublicAuthorityDto`, un salto más— es [`28`](28.user-story.md) y necesita resolución de tipos. Esta user story cubre lo que se ve en la firma.

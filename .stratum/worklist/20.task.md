# Definir la `api` de lattice, con su CLI como primer cliente y el proveedor `bilink` usándola

Es la que **valida la forma** que fijó [`1z`](1z.task.md), y por dos motivos a la vez: es un segundo subsistema, y trae el primer consumidor que **no es una CLI**.

## Dos clientes, y el segundo es el que prueba algo

**La CLI de lattice**, igual que en bilinker: si puede hacer su trabajo contra `api`, la api está completa.

**Y el proveedor `bilink`**, que hoy compone por texto:

```rust
let args = vec!["graph", ".", "--format", "json"];
let out = Command::new(&self.binary).args(&args).current_dir(scope).output()?;
```

Arma argumentos y parsea la salida. El contrato es **un JSON sin esquema**: si bilinker le cambia un campo, lattice se entera en runtime. Con la api de `1z`, el contrato lo chequea el compilador.

Es también el primer caso donde se ve si una api sirve para algo que no sea imprimir: un proveedor no formatea, transforma.

## Lo que cambia en `available()`

El proveedor distingue hoy dos indisponibilidades:

```rust
if !scope.join(".bilink").exists() { return Unavailable { "la capa no tiene .bilink/" } }
match Command::new(&self.binary).arg("--version") { … }  // ← "no se encontró el ejecutable"
```

La primera es del **repo** y se queda. La segunda es del **entorno** y desaparece: si compila, bilinker está.

**No se toca el proveedor `lsp`.** Su `Degraded` —*"el daemon recién arrancó y el language server está indexando"*— es el que sostiene la propagación de degradación de lattice, y su causa es un proceso que tiene que vivir entre invocaciones. Ese sigue como está.

## Cuándo está hecha

- `crates/lattice/src/api.rs` expone los verbos de lattice con tipos.
- `lattice-cli` no importa nada de `lattice::` que no sea `api`.
- El proveedor `bilink` llama a la api de bilinker en vez de armar argumentos y parsear JSON.
- `available()` del proveedor `bilink` conserva la causa que es del repo y pierde la del entorno, **y la spec lo dice**.
- El proveedor `lsp` no cambia.

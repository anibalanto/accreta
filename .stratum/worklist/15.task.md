# Un endpoint que no resuelve no dice qué buscaba

`bilinker get` sobre un endpoint `UNRESOLVED` falla sin decir a dónde apuntaba:

```
$ bilinker get be2e3fd6.1
Error: query matched nothing in crates/bilinker/src/apply.rs
```

Dice el archivo y nada más. **La query —que es la que dice qué fragmento se buscaba— no aparece**, y es justo el dato que hace falta para arreglarlo: el estado ya dijo que el fragmento no está; lo que falta saber es cuál era, para decidir a dónde repuntarlo.

## Por qué importa

`UNRESOLVED` es el estado que **obliga** a intervenir a mano: no tiene fix automático y no se resuelve aceptando. `recapture` existe para eso, y para usarlo hay que saber qué se está repuntando.

Sin el comando, la salida es abrir el `.yaml` del capture y leerlo. Eso es exactamente lo que el formato evita pedirle a nadie —ningún archivo de bilinker se escribe ni se lee a mano— y además es frágil: el capture se referencia por un id de 32 hex que hay que sacar del bilink primero.

Apareció migrando los 27 endpoints no resueltos del corte de formato: hubo que grepear los `.yaml` de cada uno para saber qué símbolo buscaba cada capture.

## Qué haría falta

Que `get` sobre un endpoint que no resuelve **muestre la referencia igual**, y falle después:

```
$ bilinker get be2e3fd6.1
# crates/bilinker/src/apply.rs
# capture 1a2b3c4d…  (UNANCHORED)
query: (function_item name: (identifier) @n0 (#eq? @n0 "compute_fix")) @target

El anchor `compute_fix` no está en el archivo.
Repuntar con `bilinker recapture be2e3fd6.1 <archivo> <línea>:<col>`.
```

Es la misma familia que la task `10` —`apply` culpando a git cuando el que cambió fue el anchor— y que la `v`: **la salida no es fiel a lo que la herramienta sabe.** El capture está ahí, se leyó para intentar resolverlo, y lo que se imprime no lo incluye.

## Cuándo está hecha

`bilinker get` sobre un endpoint en cualquier estado no resuelto imprime el archivo, el id del capture y su query, con un test que lo fija.

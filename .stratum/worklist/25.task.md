# `new` recibe N posiciones, y la salida deja ver qué se capturó

Señalás con el cursor las partes que querés, y bilinker genera la query que las encuentra. Las posiciones **se descartan**, que es lo que [`capture.md`](../../subsystems/bilinker/concepts/capture.md) ya dice para una y acá vale para varias:

> la selección con la que se crea sirve para **encontrar** el nodo y después se descarta

## La forma

```
bilinker new <extremo> <extremo>
```

Donde un extremo es un path con **una o más posiciones**, `abstract`, o `repo <alias>`. Los dos ejes no se pisan: las posiciones dicen *qué capturar de este lado*, y `abstract` dice *qué hay del otro*.

## La salida es la mitad del valor

Un capture es opaco después de escrito, así que si la query salió mal se descubre tarde. La salida tiene que dejar ver **lo capturado y lo que quedó afuera**:

```

el cuerpo queda afuera: un refactor adentro no dispara drift

     ⋮

```

Cuatro cosas, y cada una atrapa un error distinto:

- **el archivo como encabezado**, una vez — no repetido por fragmento
- **contexto alrededor**, con `⋮` donde se saltan líneas
- **`▸` sobre lo capturado**, así el cuerpo se ve *sin marcar*: se entiende de un vistazo que no entra
- **una línea que dice qué quedó afuera**, porque es lo que más se malinterpreta

El error que esto atrapa —y que motivó la salida— es el plugin agarrando el `@GetMapping` equivocado en un controller de veinte métodos: se ve porque la línea marcada queda lejos de la firma marcada.

## Y las marcas se editan

Confirmar con `y/N` obliga a volver a empezar cuando el plugin agarró mal. Abrir eso mismo en el editor deja **corregirlo ahí**: sacás un `▸`, ponés otro, guardás. Es el patrón de `git rebase -i` y `git add -e`.

**Y las marcas son señales, no rangos.** Cada línea marcada resuelve a su nodo, igual que hoy una posición resuelve al nodo con nombre más cercano — así que editar el buffer es otra forma de señalar, y lo que se guarda sigue siendo la query.

**El editor es el de git**, con `git var GIT_EDITOR`: contesta lo que git realmente usaría, respetando `$GIT_EDITOR` → `core.editor` → `$VISUAL` → `$EDITOR` → el fallback del sistema. Es el mismo mecanismo que [`1n`](1n.task.md) terminó usando para `agree`, cuando leer `user.name` resultó ser la fuente equivocada.

Sin `$EDITOR` y sin `core.editor`, queda el `y/N`.

## Cuándo está hecha

- `new` acepta más de una posición por extremo y genera una query con N `@target`.
- La salida muestra el archivo una vez, con contexto y con lo capturado marcado.
- Dice explícitamente qué quedó afuera.
- Las marcas se editan en el editor de git, y lo editado es lo que se captura.
- Sin editor configurado, degrada al `y/N`.
- Con `--dry-run` no escribe y muestra lo mismo.
- Un extremo `abstract` sigue funcionando igual: no tiene posiciones ni modo.

## Lo que no entra

**El renombre de `chain new` a `new`.** Vale la pena —*cadena* es vocabulario interno y quien usa la herramienta crea un bilink— pero es un cambio de nombre que toca la spec de `chain`, y va aparte.

# `new` recibe N posiciones, y la salida deja ver qué se capturó

Señalás con el cursor las partes que querés, y bilinker genera la query que las encuentra. Las posiciones **se descartan**, que es lo que [`capture.md`](../../subsystems/bilinker/concepts/capture.md) ya dice para una y acá vale para varias:

> la selección con la que se crea sirve para **encontrar** el nodo y después se descarta

## La forma

```
bilinker new <extremo> <extremo>
```

Donde un extremo es un path con **una o más posiciones**, `abstract`, o `repo <alias>`. Los dos ejes no se pisan: las posiciones dicen *qué capturar de este lado*, y `abstract` dice *qué hay del otro*.

## La salida es la mitad del valor

Un capture es opaco después de escrito, así que si la query salió mal se descubre tarde. La salida tiene que dejar ver **lo capturado y lo que quedó afuera**:

```
$ bilinker new --as spring-controller docs/spec.md:12:1 Controller.java:16:5

     ⋮
     14       @Operation(summary = "Permisos del usuario del token")
  ▸  15       @GetMapping("/permissions/from-token")
  ▸  16       public List<PublicAuthorityDto> getPermissions(
  ▸  17               @RequestHeader("Authorization") String token)

     19           return service.permissionsOf(token);

el cuerpo queda afuera: un refactor adentro no dispara drift

docs/spec.md
     12   ## Permisos del usuario
     ⋮

¿escribir? [y/N]
```

Cuatro cosas, y cada una atrapa un error distinto:

- **el archivo como encabezado**, una vez — no repetido por fragmento
- **contexto alrededor**, con `⋮` donde se saltan líneas
- **`▸` sobre lo capturado**, así el cuerpo se ve *sin marcar*: se entiende de un vistazo que no entra
- **una línea que dice qué quedó afuera**, porque es lo que más se malinterpreta

El error que esto atrapa —y que motivó la salida— es el plugin agarrando el `@GetMapping` equivocado en un controller de veinte métodos: se ve porque la línea marcada queda lejos de la firma marcada.

## Y las marcas se editan

Confirmar con `y/N` obliga a volver a empezar cuando el plugin agarró mal. Abrir eso mismo en el editor deja **corregirlo ahí**: sacás un `▸`, ponés otro, guardás. Es el patrón de `git rebase -i` y `git add -e`.

**Y las marcas son señales, no rangos.** Cada línea marcada resuelve a su nodo, igual que hoy una posición resuelve al nodo con nombre más cercano — así que editar el buffer es otra forma de señalar, y lo que se guarda sigue siendo la query.

**El editor es el de git**, con `git var GIT_EDITOR`: contesta lo que git realmente usaría, respetando `$GIT_EDITOR` → `core.editor` → `$VISUAL` → `$EDITOR` → el fallback del sistema. Es el mismo mecanismo que [`1n`](1n.task.md) terminó usando para `agree`, cuando leer `user.name` resultó ser la fuente equivocada.

Sin `$EDITOR` y sin `core.editor`, queda el `y/N`.

## Cuándo está hecha

- `new` acepta más de una posición por extremo y genera una query con N `@target`.
- La salida muestra el archivo una vez, con contexto y con lo capturado marcado.
- Dice explícitamente qué quedó afuera.
- Las marcas se editan en el editor de git, y lo editado es lo que se captura.
- Sin editor configurado, degrada al `y/N`.
- Con `--dry-run` no escribe y muestra lo mismo.
- Un extremo `abstract` sigue funcionando igual: no tiene posiciones ni modo.

## Lo que no entra

**El renombre de `chain new` a `new`.** Vale la pena —*cadena* es vocabulario interno y quien usa la herramienta crea un bilink— pero es un cambio de nombre que toca la spec de `chain`, y va aparte.

## Cómo cerró

Sobre `chain new`, no sobre `new`: el renombre sigue afuera. Las posiciones extra van por coma —`Foo.java:2:5,10:5`— porque repetir el flag ya significa *el otro extremo* y encadenarlas con `:` sería ambiguo con un path que lleve números.

### Lo que hace que sean N partes y no N captures

**Un solo ancla.** El patrón se enraiza en el ancla estable que contiene a todas las partes, y de ahí baja por los caminos fundidos en un árbol. Eso es lo que las ancla *entre sí* —`@RequestMapping` **de la clase que contiene** al método— y es exactamente lo que [`24`](24.task.md) argumentaba al descartar la lista de queries. Con una sola posición el ancla es la de siempre, así que una query de un `@target` sale idéntica a la que salía.

### Dos cosas que sólo se ven implementando

**Las partes salen en orden de archivo, y no por prolijidad.** tree-sitter exige que los hijos de un patrón vayan en el orden de la gramática: emitir el nombre primero por costumbre da *Impossible pattern* en cuanto una parte cae en los modificadores, que en Java es donde están las anotaciones — el caso que motiva todo el sprint. Así que el predicado de nombre se ordena junto con las partes, por posición.

**Ninguna parte puede contener a otra**, y es una invariante nueva del formato. Salió del primer intento real: señalar el `@RequestMapping` de la clase resuelve **a la clase**, porque una anotación no es un ancla estable y el walk-up sigue hasta la declaración. Con el método señalado también, el fragmento habría sido *clase + método*, con el método contado dos veces. Se rechaza y se dice cuál está adentro de cuál.

Eso deja claro dónde termina esta task: **`chain new` con posiciones no alcanza el caso de Spring**. No es una limitación de las N posiciones, es que el nodo que hay que señalar no es un ancla estable — y elegirlo es lo que hace el plugin de [`27`](27.task.md).

### La vista, y por qué se edita en un solo buffer

Abrir un editor por tip haría corregir a ciegas el segundo. Lo que se revisa es el vínculo, no cada punta por su cuenta, así que los dos van en un buffer y al guardar la vista corregida se vuelve a mostrar. Un buffer sin ninguna marca no escribe nada: es la forma de abortar, la misma que `git commit` con un mensaje vacío.

**Sin terminal no se pregunta y se escribe.** Un `chain new` adentro de un script no puede esperar una tecla que nadie va a apretar; `--yes` es cómo se dice eso explícitamente y `--dry-run` cómo se pide sólo la vista.

### Y destapó un defecto de generación

Bilinkear la sección `#### El separador es \n` que [`24`](24.task.md) acababa de escribir **falla**: el texto del ancla entra crudo en el predicado, y adentro de una query `\n` es un salto de línea. La que reescribe el nombre al reanclar sí escapa; la que lo escribe la primera vez, no. Quedó como [`2d`](2d.task.md), con el caso peor anotado: un `"` en el nombre no da una query que no matchea, da una query inválida.

Por eso esa sección es la única de las cinco nuevas que **no tiene bilink todavía**.

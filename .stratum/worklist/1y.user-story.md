# Cada subsistema expone una API, y su CLI es el primer cliente

**Lado:** desarrollo. Es el **medio**, no un fin: lo que entrega valor es [`23`](23.user-story.md), y esto es lo que la hace escribible.

Como quien va a escribir impact, quiero que **componer dos subsistemas sea llamar funciones y no armar procesos**, para que un orquestador sea Rust y no un ensamblador de líneas de comando y parseo de salidas.

## Por qué, y no es la performance

Hoy la composición cruza una frontera de texto. Se ve en el proveedor `bilink` de lattice:

```rust
let args = vec!["graph", ".", "--format", "json"];
let out = Command::new(&self.binary).args(&args).current_dir(scope).output()?;
```

Arma argumentos y parsea la salida. Funciona, y el contrato es **un JSON sin esquema**: si bilinker le cambia un campo, lattice se entera en runtime. Una API tipada lo vuelve un contrato que el compilador chequea.

Y el que viene es peor: [ADR-0001 de impact](../../subsystems/impact/.stratum/impl/docs/adr/0001-orquesta-no-escribe.md) lo pone a componer **dos** subsistemas —lattice le da los vecinos, bilinker hashea y escribe— para una sola decisión. Eso con procesos son dos formatos de salida que parsear y dos vocabularios de error que traducir.

## La mitad ya está hecha

Los cuatro subsistemas **ya tienen** la separación:

| | lib | cli | |
|---|---|---|---|
| bilinker | `crates/bilinker` | `crates/bilinker-cli` | |
| stratum | `crates/stratum` | `crates/stratum-cli` | |
| lattice | `crates/lattice` | `crates/lattice-cli` | |
| impact | `crates/impact` | `crates/impact-cli` | **vacíos** — spec sin impl |
| accreta | — | — | **no tiene capa de impl** |

Y el mecanismo entre repos también: bilinker depende de stratum así, en cinco crates.

```toml
stratum = { git = "https://github.com/anibalanto/stratum.git", branch = "main" }
```

**Lo que falta no es la separación: es que la lib tenga una superficie declarada.** Hoy es todo lo que quedó `pub`, que es otra cosa.

## La regla

> **Cada subsistema define una `api`, y su propia CLI es el primer cliente.**

Las dos mitades importan:

**"Define una api"** — un módulo con los verbos del subsistema, tipados, y nada más. No la lib entera: lo demás queda fuera del alcance de un consumidor.

**"Su CLI es el primer cliente"** — y esto es lo que hace que la regla se sostenga sola. Si la CLI no puede hacer su trabajo con la api, la api está incompleta, y se nota al escribirla en vez de al integrarla. Es también lo que garantiza lo que se pidió: que la api exponga **lo mismo** que la línea de comandos, no una versión parecida.

**Y "primer" quiere decir que puede haber otros.** Una API REST, una app de escritorio, un servidor de LSP. La CLI deja de ser *la* interfaz y pasa a ser *una*.

## Lo que hay que cuidar, y es lo único caro

[ADR-0001](../../subsystems/impact/.stratum/impl/docs/adr/0001-orquesta-no-escribe.md) decide:

> Impact **puede invocar** a bilinker. Impact **no puede parsear** su formato ni escribir sus archivos.

**Con procesos esa regla es imposible de violar**: por el pipe pasa texto, y `BiLink::load` no está al alcance. Como dependencia, impact importaría la lib entera y podría parsear el formato.

Por eso la api tiene que ser **angosta**: si no reexporta los tipos del formato, la regla sigue siendo estructural y no disciplina. La frontera se muda del proceso al módulo, y **sigue siendo una frontera**.

Es el mismo criterio que el proyecto ya aplicó al separar [`bilink-format`](../../subsystems/bilinker/concepts/format-version.md) — *"sólo los tipos y su serialización: no resuelve queries, no consulta git"*, publicado *"para que un consumidor valide sin adoptar bilinker"*. El formato se comparte como crate; **las operaciones se piden**.

## Lo que se pierde

Una causa de indisponibilidad. El proveedor `bilink` de lattice hoy distingue dos:

```rust
if !scope.join(".bilink").exists() { return Unavailable { "la capa no tiene .bilink/" } }
match Command::new(&self.binary).arg("--version") { … }  // ← "no está instalado"
```

La primera es del **repo** y sobrevive. La segunda es del **entorno** y desaparece: si compila, está.

**No se pierde el gradiente**, que era la duda. `Degraded` —*"responde pero incompleto"*— lo produce sólo el proveedor `lsp`, y su causa es el daemon indexando. Ese sigue siendo un proceso, porque tiene que vivir entre invocaciones.

## Las tasks

| | |
|---|---|
| [`1z`](1z.task.md) | la `api` de bilinker, con su CLI como primer cliente |
| [`20`](20.task.md) | la `api` de lattice, con su CLI como primer cliente y el proveedor `bilink` usándola |
| [`21`](21.task.md) | la capa de implementación de accreta: su `api`, y su CLI como primer cliente |
| [`22`](22.task.md) | el orquestador es accreta, y `invocar` deja de significar `Command::new` |

**El orden es ése**, y no por gusto: `1z` fija la forma, `20` la valida contra un segundo subsistema —y contra un consumidor que no es una CLI—, y `21` es el que la usa para lo que existe. `22` va al final porque recién ahí se sabe qué decir.

**Impact no tiene task acá.** Sus `crates/` están vacíos y siguen así: es el único subsistema que es spec pura, y su trabajo —evaluar si un cambio es coherente con los documentos de decisión que lo gobiernan— es el más lejano de los cinco. Cuando tenga impl, cumple la misma regla.

## Cuándo está hecha

- Bilinker, lattice y accreta exponen un módulo `api` con sus verbos tipados.
- Cada CLI está escrita **contra su propia api**, sin tocar nada de la lib que la api no exponga.
- El proveedor `bilink` de lattice consume la api de bilinker en vez de armar argumentos y parsear JSON.
- Ninguna api reexporta los tipos del formato de otro subsistema.
- Está decidido y escrito que el orquestador es accreta, y qué significa hoy "invocar".

## Lo que no entra

**El daemon del LSP sigue siendo un proceso.** Tiene que vivir entre invocaciones y sostener su índice; ahí `Degraded` conserva todo su sentido.

**Y no se publica en crates.io.** La dependencia sigue siendo por git, como la de stratum: la api es un compromiso **entre los subsistemas de accreta**, no una superficie pública. Si algún día lo es, eso es otra decisión.

# La query captura varios `@target`, y el fragmento es la concatenación

Es **el único mecanismo nuevo** de [`23`](23.user-story.md); todo lo demás es cómo se genera la query.

Hoy `query.rs` toma el primero y descarta el resto:

```rust
let target_idx = query.capture_index_for_name("target")?;
// … devuelve Option<(usize, usize)> — un solo rango
```

## Qué cambia

`find_target` devuelve **los rangos, en orden de aparición en el archivo**. El fragmento es su concatenación; el `hash` se calcula sobre eso.

Y con un solo `@target` el comportamiento es **idéntico al de hoy** — que es lo que permite que los 190 bilinks existentes no se enteren.

## Por qué no son rangos de bytes

Es la alternativa obvia y rompe lo que bilinker existe para hacer: `[from:to]` se invalida con cualquier edición más arriba del archivo. Una query con varias capturas **sobrevive a que el código se mueva**, que es la propiedad central.

## El separador es `\n`, y se elige una vez

Los fragmentos no son contiguos, así que hay que decidir qué va en el medio — y eso **entra en el `hash`**:

```
@RequestMapping("/public-api/user")│???│@GetMapping("/permissions/from-token")
```

| | |
|---|---|
| nada | dos capturas pegadas producen un texto que no existe en ningún archivo |
| **`\n`** | **elegido**: legible, y estable frente a cuánto espacio haya en el medio |
| el texto intermedio | es el archivo tal cual, pero entonces el cuerpo entra por la ventana cuando dos capturas lo tienen en el medio |

**Y no se vuelve a tocar.** Cambiarlo después movería el hash de todos los captures multi-fragmento, y **todos pasarían a `ALTERED` sin que nadie tocara el código** — drift fabricado por un cambio de opinión, que es lo que la task `18` ya costó una vez con el recorte de bordes.

**El `hash_ast` sigue la misma regla**: las s-expressions de los nodos, en el mismo orden, unidas por `\n`.

## Por qué una query y no una lista de queries

`query` podría pasar de `Option<String>` a una lista, con una query por fragmento. Es más fácil de generar y más legible, y se descarta por dos razones:

**Pierde el anclaje relativo.** Una query con varios `@target` dice *"el `@RequestMapping` **de la clase que contiene** al método `getPermissions`"*. Con una lista, cada query se ancla sola y la primera sería *"el `@RequestMapping`"* a secas — que en un archivo con dos clases matchea la equivocada. Se arregla repitiendo el contexto en cada una, o sea reconstruyendo a mano lo que el patrón único ya expresa.

**Y abre la resolución parcial**, que hoy no existe. Si dos de tres queries resuelven, eso no es `RESOLVED` ni `UNANCHORED`: es un fragmento a medias, y habría que inventarle un estado y decidir si se hashea lo que hay. Con una query única, tree-sitter **matchea el patrón entero o no** — y esa dicotomía es la que todo el modelo de estados asume.

Menor pero cierto: el id es `sha256(file \0 query \0)`. Con `String` la fórmula no cambia; con lista habría que definir cómo se hashea una, y es una decisión más donde equivocarse.

**Lo que la lista sí hacía mejor es la legibilidad.** Una query de cuatro `@target` no se lee de un vistazo — y para eso está `history`, que muestra el `{file, query}` de cada capture.

## Cuándo está hecha

- Una query con N `@target` produce un fragmento de N partes, en orden de archivo.
- Con un `@target`, el hash de un capture existente **no cambia**.
- El separador es `\n`, está escrito en `concepts/capture.md`, y hay un test que lo fija.
- `concepts/capture.md` § *"Nombra un nodo entero"* pasa a decir *"un conjunto estructural de nodos"*, sin perder lo que defendía: que no hay sub-rangos posicionales.

## Lo que no entra

Cómo se generan esas queries. Eso es [`25`](25.task.md), [`26`](26.task.md) y [`27`](27.task.md).

## Cómo cerró

El mecanismo salió como estaba escrito: `find_target_with_sexp` pasó a ser `find_fragment` y devuelve **todos** los `@target` del primer match, ordenados por posición en el archivo. El fragmento —lo que se hashea— dejó de ser un `&str` recortado del source y pasó a ser un tipo, `Ranges`, que **no se puede construir vacío**: un fragmento sin partes no es un fragmento vacío, es que la query no resolvió, y eso ya se decía con `None`.

El separador vive en un solo lugar, `bilink_format::FRAGMENT_SEPARATOR`, y de ahí lo toman el texto y el `hash_ast`.

### El derivado que había que abrir era la cache, no el bilink

El formato en git no cambió —`query` sigue siendo un string— pero **`range` sí**: era un `start~end` y pasó a ser uno por parte, separados por coma. Está fuera de git y fuera del esquema publicado, así que no costó nada; lo que costó fue que el rango único estaba asumido en seis lugares —`check`, `accept`, `get`, `capture`, `frontier`, el LSP y el JSON hacia lattice— y cada uno tenía su propia forma de rebanar el source. Ahora todos piden `ranges.text(&source)`.

El único que no se pudo hacer literal es el `commit` del contenido aceptado: `git log -L` toma **un** tramo de líneas, así que se le pregunta por el que abarca todas las partes. Da un commit igual o más nuevo que el del fragmento solo, y sirve igual — lo que hace falta es un commit desde el cual el fragmento no cambió, y si el tramo entero no cambió, el fragmento tampoco.

### Y `get` tenía un par de líneas que ya no podía decir

`GetResult` llevaba `start_line`/`end_line`. Con un fragmento de dos partes ese par sólo puede mentir: o nombra el tramo que las abarca —que incluye lo que el fragmento **no** cubre— o nombra una sola. Pasó a ser una lista de tramos, uno por parte, y la salida los imprime todos: `lines 12–12, 40–43`.

### Sube a formato 3.3.0, y el guard no se habría enterado

Los tipos no cambiaron y ningún archivo existente cambia de hash. Sube igual, por el motivo de siempre: un parser de `3.2.0` lee una query de tres `@target`, se queda con el primero, y hashea otro fragmento **en silencio**.

Lo que este caso destapó es el **límite del guard de esquema**: la regla es *"lo que discrimina al parsear tiene que ser visible en el esquema"*, y acá lo que discrimina está adentro de un string. Ningún tipo lo hace visible, así que el hash del esquema no se habría movido solo — se movió porque cambió un doc comment. Quedó escrito en [`concepts/format-version.md`](../../subsystems/bilinker/concepts/format-version.md) § *"Y a veces no se puede"*, que es donde alguien lo va a buscar la próxima vez.
